## 3. 新发现 `H1`~`H4`

### H1 · `logs/` 是 `.gitignore` 目录，而 `19` 与 `20` 对"能不能删"给了**相反**的指示（🟠 中高）

**事实（逐条读到实证）**

1. [.gitignore](../.gitignore) 含 `logs/` 与 `*.log`。
2. `logs/` 里目前同时躺着三类东西：
   - **11 个脚本/对照**：`auth-chain.js`、`contrast.js`、`firstload.js`、`inspect-pages.js`、`probe.js`、`probe-register-token.js`、`measure.js`、`measure-interaction.js`、`capture.js`、`detector-control.html`、`detector-control-linked.{html,css}`；
   - **运行期日志**：`ruankao-server.log` **142KB**、`ruankao-server.log.2026-09-27.0.gz`、`rk-boot.log`、`rk-boot2.log`、`vite2.log` 32KB、`chrome-cdp.log`、`preview.log`、`question-server.log`；
   - **JSON 取样**：`me.json`、`proxy.json`、`subj.json`。
3. 仓库 **0 次提交**（§2.5 已核），`scripts/` 目录**不存在**（README §3 与 `10 §10.3` 都声明了它），`web/package.json` 的 `scripts` 里**没有任何入口**指向 `logs/*.js`。
4. **两份文档给了相反的指示**：

| 文档 | 原话 | 指向 |
| --- | --- | --- |
| [19 §5](19-p2-frontend-open-items.md) | "本轮新增的可复现脚本（都在 `logs/`，**非产物、可删**）" | **可以删** |
| [20 §4.3](20-p2-verification-round.md) | "这两个对照文件已作为**永久阳性对照**保留在 `logs/`，**不要再删**" | **绝不能删** |

**后果**：三件事叠加后，"永久"是假的，而且**存在一条具体的销毁路径**——

- 按 `19 §5` 的授权执行一次"清理非产物"或 `git clean -xdf`（清 ignored 文件的标准动作），`20 §4.3` 声称永不删除的对照文件会**永久消失**；
- `logs/` 同时是**应用日志的默认落点**（`application.yml` 的 `RK_LOG_DIR` 默认 `logs`），所以"清理日志"与"销毁验证基础设施"是**同一个动作**；
- 换机器或重新 clone，这批脚本全部为零——而 `20` 把三页的回测结果、`F10` 的首屏数字、检测器结论**全挂在这批脚本上**。

**为什么这条是本节最重的**：`20` 的整章都在讲"错的仪器会持续产出看起来可信的错数字"，而它自己把仪器放在了一个会被常规操作删掉、且不进版本控制的地方。

**建议（下一轮执行，本轮未做）**：

1. 把验证脚本搬到 `scripts/`（README §3 已声明的"离线工具"落点，如 `scripts/verify/`），`logs/` 只留运行期输出；
2. 或在 `.gitignore` 补否定项：`!logs/*.js`、`!logs/detector-control*`（成本最低的过渡方案，但**没有解决"日志与脚本同目录"这个根**）；
3. **删除 `19 §5` 那句"非产物、可删"**——它是错的授权（`19` 是留痕文档，按约定不回改，故应在下一轮的记录文档里显式作废它）；
4. 立即做首次 `git commit`（见 §6.4），否则以上三条都只是在磁盘上搬文件。

**建议**：把该条从"回填颜色"扩为"**重写 `07 §7.9` 的主题定制段**"——颜色改 `#2a72c2`；机制改写成"`@forward` 在 `importStyle: 'css'` 下是死代码，实际靠 `:root` 运行期变量覆盖，派生档按 Element Plus 的混合公式现算"；同时按 [18 §270](18-p2-frontend-deviations.md) 的建议改写 §7.10 的预算式子（去掉不存在的 chunk 名，改用"首屏同源传输字节"表述）。

### H4 · 判据类：我自己在复现过程中得到过一个**假阴性**，差点据此否定一个正确结论（🔵 低，但值得留）

**事实**：我核 `20 §2.2` 那句"`UserServiceImpl` 第 98 行"时，用区分大小写的模式检索 `lastLoginAt|last_login_at` → **零命中**，一度认定该引用是编造的。改用 `lastLogin|LastLogin` 后确认：`UserServiceImpl:98` 是 `sysUserMapper.updateLastLoginAt(...)`、L99 是 `user.setLastLoginAt(now)`——**引用完全准确**。

**成因**：驼峰里的大写 `L`（`updateLastLoginAt` / `setLastLoginAt`）不在我的模式里。

**判据（给下一个做核实的人）**：查"某符号是否在某文件出现"时，驼峰要么放宽大小写（`-i`），要么把小写/驼峰两种写法都列进模式；否则会得到**假阴性**，并据此去否定一个正确的结论。

**这条与 `20 §4.2` 的 `probe.js` 坑同源**：那次是 `if (r.cssRules)` 把"空对象是 truthy"当成"有子规则"，这次是"模式没命中"被当成"代码里没有"。**两次都是检索/判断方式错了，却当成被测对象的问题。** 本项目已因此栽过三轮（`12` 的假 ✅、`13` 的方法批评、`20` 的仪器 bug），所以记成判据而不只是记成一次失误。
