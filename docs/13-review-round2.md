## 13.2 G1 场次二 `PENDING` 时会话无终止路径 — 中高

**性质：这是两个各自正确的修订交互出来的新缺陷**（A5 引入场次模型 + B9 收紧历史列表过滤），单独看任一方都没有问题。

### 13.2.1 三处机制叠加

| # | 机制 | 出处 |
| --- | --- | --- |
| ① | 兜底任务只扫 `status = 'IN_PROGRESS'` 的**场次**；场次二为 `PENDING`（`started_at` 为 NULL）**永不匹配** | [06-backend.md](06-backend.md) §6.9.2 兜底项、§6.13 超时会话结算 |
| ② | 「过期数据清理」只清 `ABANDONED` 且 >90 天 → `IN_PROGRESS` 不在清理范围 | [06-backend.md](06-backend.md) §6.13 |
| ③ | **B9 的落点**：`GET /exams` 默认只返回 `SUBMITTED`/`SCORED`；`includeAbandoned = true` **也不含 `IN_PROGRESS`** | [05-api.md:401](05-api.md#L401) |

### 13.2.2 触发场景与后果

**场景**：高级科目考生考完上午连考，合上电脑；午休后不再回来（或换设备后忘了继续）。

场次一到期 → 按 §6.9.2 惰性/兜底逻辑置 `FINISHED`，场次二置 `PENDING`（**这是设计要的行为**）→ 但会话 `status` 仍是 `IN_PROGRESS`，而**没有任何机制会再推进它**：

1. **新建模拟考被拦住**：`4003`「存在未完成的模拟考」——[06-backend.md](06-backend.md) §6.9.3 的条件是「无 `CREATED`/`IN_PROGRESS` 的会话」
2. **该会话不在历史列表里 —— 用户没有 UI 入口回去处理它**：默认口径只返回 `SUBMITTED`/`SCORED`，`includeAbandoned = true` 也拿不到 `IN_PROGRESS`。用户只能靠手工拼 URL 进详情页
3. **场次一的成绩不判分**：判分发生在交卷时（§6.9.2 状态流转），用户白考一场

### 13.2.3 影响范围恰好是高级科目

初级/中级**完全不受影响**：只有一个场次，`remainingSec == 0` 时命中「已是最后一场次则触发整卷交卷」，直接进 `SUBMITTED`。

→ **该缺陷的触发面正好是 A5 要服务的高级科目**（也是本次修订的动因），属于"改动目的达成、改动副作用落在同一处"的典型。

### 13.2.4 修复建议（待裁决时间阈值）

在 [06-backend.md](06-backend.md) §6.13 的「超时会话结算」补一条：

> **会话级滞留结算**：`exam_session.status = 'IN_PROGRESS'` 且当前场次为 `PENDING`，且**上一场次的 `finished_at` 早于 `NOW() - {阈值} 小时`** → 按 [05-api.md](05-api.md) 用例 23 已定的语义**自动交卷**（未作答的场次一并置 `FINISHED`，成绩页标 `answered = false`）。

**两个设计要点**：

- **用 `finished_at` 而非 `updated_at` 作判据**：`GET /exams/{id}` 是读操作不写库，若以 `updated_at` 判"无活动"会漏判（用户反复查看详情页会不断刷新时间戳）。`exam_session_sitting.finished_at` 是确定性来源。
- **选"自动交卷"而非"自动放弃"**：自动交卷保留考生场次一的成绩，且完全复用 05 用例 23 已定义的语义（"仍有 `PENDING` 场次 → 一并置 `FINISHED`、标注未作答"），不引入新的状态语义。

**阈值待裁决**：建议 **6 小时**（覆盖午休 → 当晚，且远小于论文场次的 120 分钟，不会误伤"正在午休、下午会回来"的考生）。若你认为需要更保守，**12 小时**亦可；阈值应写入 `sys_config`（与 §6.13 其他任务一样由 `task.enabled.*` 系列开关控制）。

**附带收益**：这条修完后，②的「过期数据清理」任务才有 `ABANDONED` 对象可清——当前自动路径根本不产生 `ABANDONED`（只有用户主动点放弃才产生）。

## 13.3 G2 `exam_session_section` 漏快照 `sitting_no` 与 `support_status` — 高

### 13.3.1 事实

[04-database.md:477-497](04-database.md#L477-L497) 的 `exam_session_section` 实际列：

```
id / session_id / section_no / section_name / section_type / question_count /
max_score / objective_score / duration_min / duration_max / allow_early_submit /
used_sec / status / started_at / finished_at
```

**没有 `sitting_no`，也没有 `support_status`。**

### 13.3.2 但下游两处必需这两个字段

| 需求 | 出处 |
| --- | --- |
| `SectionVO.sittingNo`（成绩页与详情页按场次分区展示） | [05-api.md](05-api.md) `SectionVO`：`sittingNo` 标注「所属场次」；`ExamSessionVO.sections` 定义为「全场次分节的**扁平列表（含 `sittingNo`）**」 |
| `ExamResultVO.sectionResults[].sittingNo` + `.supportStatus` | [05-api.md:392](05-api.md#L392) |
| `NOT_SUPPORTED` 分节在成绩页展示「本平台无法模拟」 | [06-backend.md:350](06-backend.md#L350) |

### 13.3.3 为什么"JOIN 回模板表"不是可接受的替代

唯一取值途径是经 `exam_session.template_id` JOIN 回 `exam_paper_section`。但这**恰好破坏快照要保的东西**：

- [04-database.md:499-501](04-database.md#L499-L501) 的注释写明快照的目的：「保证历史成绩在题目被编辑或下架后仍可复现」
- [03-architecture.md](03-architecture.md) **ADR-04** 明说模板驱动的原因之一是「**允许管理员在发现配置错误时自行修正**」

→ 管理员修正一次卷面模板（例如把某分节从场次一挪到场次二，或修正 `support_status`），**历史成绩的场次归属与"无法模拟"标记就会随之漂移**。

### 13.3.4 这不是设计取舍，是漏列

对照：`exam_session_item` **有** `section_no`（[04-database.md:503-532](04-database.md#L503-L532)）——快照表确实在快照结构信息。所以 `exam_session_section` 缺的是两列，而非"有意不存"。

### 13.3.5 修复

`exam_session_section` 补两列，创建会话时从 `exam_paper_section` 快照：

```sql
  sitting_no          TINYINT NOT NULL COMMENT '所属场次（1/2），创建会话时从 exam_paper_section 快照',
  support_status      VARCHAR(16) NOT NULL DEFAULT 'SUPPORTED' COMMENT 'SUPPORTED / NOT_SUPPORTED，快照自模板',
```

**窗口期**：现在改是**零成本一行 DDL**；P5 之后改需要写数据迁移并回填历史会话，成本差一个量级。建议与 §13.4 合并一次性处理。

## 13.4 G3 A6 没有真正闭合：`duration_min` / `duration_max` 仍为 `INT NULL` — 中高

### 13.4.1 事实

| 出处 | 说法 |
| --- | --- |
| [04-database.md:408-409](04-database.md#L408-L409) `exam_paper_section` | `duration_min INT NULL` / `duration_max INT NULL` |
| [04-database.md:486-487](04-database.md#L486-L487) `exam_session_section` | `duration_min INT NULL` / `duration_max INT NULL` |
| [02-domain-model.md:163](02-domain-model.md#L163) | 「`duration_min` / `duration_max` **一律必填**」 |
| [05-api.md](05-api.md) §5.10 校验规则 2 | 「`durationMin`、`durationMax` **均必填**，且 `durationMin ≤ durationMax`」 |
| [06-backend.md](06-backend.md) §6.9.1 | 以 `duration_min` 作**离开门槛**、`duration_max` 作**强制离开**条件 |
| [12-changes-applied.md](12-changes-applied.md) §2.4.3 | 「在**所有**场次的所有分节上都必填（A6），否则门槛判定不可计算」 |

→ **A6 裁决的结论是"必填"，但 DDL 层面没有落任何约束。**

### 13.4.2 加重情节：当前 `NULL` 就是默认态

[12-changes-applied.md](12-changes-applied.md) §6 **L1 自己承认**：「04 §4.8.2 只给出场次/分节的**蓝图注释**，20 个科目的完整 `INSERT`（含场次与分节）**尚未落地**」，归属 P1。

也就是说：**P1 写 `init-data.sql` 时，`duration_min` 漏填不会报任何错**。而 `NOT NULL` 恰恰是建库时**唯一**能抓住漏填的机制。漏填的后果不是报错而是静默失效——`canLeaveInSec` 算不出来，该分节永远退不出去（或 NPE）。

### 13.4.3 口径不一致（更值得注意的一点）

**B7 处理的是同一类问题**（"必填" vs DDL 可空），它在 [04-database.md](04-database.md) 与 [08-ai-pipeline.md](08-ai-pipeline.md) §8.2.3 都**显式补了「由应用层强制」**的声明，并加了 `PUBLISHED` 前的校验。

A6 做了**同样的取舍却没有留这句话** → 后人读 04 会以为已经约束住了，读到 02/05 才知道是应用层要求，中间没有任何一处说明"这里是有意为之"。

### 13.4.4 两种修法（待裁决）

- **(a) 推荐：两表两列共 4 处改 `NOT NULL`。** 理由：分节不存在"不需要时长约束"的场景，`Σ(durationMin) ≤ sitting.totalDuration ≤ Σ(durationMax)` 是硬不变式（[05-api.md](05-api.md) §5.10 规则 3 已写入校验）。这与 B7 的情况**本质不同**——B7 保持可空有正当理由（`source_type` 各取值所需字段不同），A6 没有。
- **(b) 保持可空**：则必须补齐 B7 那样的显式声明（04 注释 + 05 校验说明），并加一条**建库后校验**纳入 P1 验收：
  ```sql
  SELECT COUNT(*) FROM exam_paper_section WHERE duration_min IS NULL OR duration_max IS NULL;  -- 必须为 0
  ```

> 注意：`exam_session_section` 的两列是快照列，其取值来自模板表。**若模板表改 `NOT NULL` 而会话表保持可空，则快照列仍可能为 NULL** —— 因此 (a) 方案必须两表同时改。

## 13.6 两处口径与验收标准的修正建议

### 13.6.1 12 §8 自查表的口径

- `1 最难` 在 08:440 是**有意保留的历史冲突记录**：该段自己写着「**注意这里曾出现方向冲突**：04 的 DDL 注释最初写作 `'1~5，1 最难'`，与 02 相反；现已同步为同一语义」。**这是文档资产，不是缺陷。**

**问题出在自查方法**：表格把"期望为 0"的项标成 ✅ 而实测非 0，说明该栏是**按印象勾选**而非跑检索得出。这与第一轮评审中我曾把错误码 `1003` 误判为"未被引用"是同一类坑（正则未覆盖 `code === 1003` 的写法）。

> **建议**：把口径改成可判定、可复现的表述——
> - 「无残留**字段与参数**」（而非"仅在某处出现"）
> - 「`1 最难` 仅作为历史记录出现 1 处」
>
> **理由**：自查表是后续所有验收的信任基础。**一旦出现假阳性，表里其余所有 ✅ 都要重新打折**——本次复查因此对 12 §8 的每一项都做了独立复跑，而非抽样。

### 13.6.2 P0 验收标准缺"数值一致性"检查（G9 · 流程根因）

[10-roadmap.md](10-roadmap.md) §10.2 的 P0 验收标准共 5 条：

| # | 现有验收项 | 覆盖的缺陷类型 |
| --- | --- | --- |
| 1 | 11 个文件全部存在，README 索引链接可达 | 文件完整性（**数字本身已过期，见 G6**） |
| 2 | 跨文档**命名**一致（表名/字段名写法相同） | 命名漂移 |
| 3 | `05` 错误码表与 `06` 的 `ErrorCode` 约定一致 | 枚举漂移 |
| 4 | `02` 范围外与 `01` 的 OOS 清单无矛盾 | 范围漂移 |
| 5 | 抽查 5 个接口的字段能在 `04` 找到对应列 | 字段可追溯 |

**缺口**：**没有任何一条覆盖"同一事实的数值/计数在多个文档中是否一致"。**

这正是两轮评审中占比最高的缺陷成因：

| 第一轮发现 | 表现 |
| --- | --- |
| A3 | `innodb_buffer_pool_size` 在 03 / 09 / 10 三处，出现 512M 与 1024M 两个值 |
| A4 | 容量数字在 01 / 03 / 04 三处，出现三组不同值 |
| D1 | 03 的括注算得 1430，与同行声明的 5000 不符 |
| D4 | 09 的注释声称"周备 4 周"，脚本只保留 7 天 |
| **G6（本轮）** | 表数量在 03 / 09 / 10 三处共 4 个位置，出现 25 与 27 两个值 |

→ **P0 能"通过"验收，却同时存在三组互相矛盾的容量数字**——因为验收项检查的是"结构一致性"（命名、枚举、字段可追溯），而缺陷出在"**数值一致性**"。两次评审共 47 条发现里，属于数值/计数漂移的有 6 条，占 13%。

**建议**：P0 验收补一条可执行项——

> - [ ] **数值一致性**：同一事实（表数量、科目数、题量、容量、时长、缓存 TTL、限流阈值、保留天数）在所有文档中**只有一个出处，其余处引用而非复写**；对"复写不可避免"的（如验收命令里的表数量）加 CI 检索断言

> **决策与理由**
> 这条是**流程级**修正，不是逐条改数字。G6 的 7 处、A3 的 3 处、A4 的 3 处，成因完全相同：**同一个数字被两个文档各写了一遍，然后两边各自演进**。逐条改数字只能修好当前这 13 处，下一个改动还会产生新的。真正有效的做法是加一条"复写即违约"的验收项，并把可自动化的部分（表数量、科目数）落成 CI 断言——这与 08 已经采用的 `check-no-corpus-files` 是同一手法。
