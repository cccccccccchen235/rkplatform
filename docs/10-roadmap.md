# 10 · 开发路线图与验收标准

> 本文件是执行排期与自检依据。每个阶段都有**可观察的验收标准**——达不到就不进入下一阶段，避免"功能都写了一半但一个都跑不通"。

## 10.1 阶段总览

| 阶段 | 目标 | 依赖 | 关键文档 |
| --- | --- | --- | --- |
| P0 | 设计定稿 | — | 全部设计文档（README + `docs/01`~`docs/14`） |
| P1 | 骨架跑通（注册登录 + 空壳页面） | P0 | 03、04、05、09 |
| P2 | 内容结构可见（科目 / 大纲 / 知识点） | P1 | 02、04、05 |

| P4 | 练习闭环（刷题 + 判分 + 错题本 + 收藏） | P3 | 05、06 |
| P5 | 模拟机考闭环 | P4 | 02、05、06 |
| P6 | 学习数据统计 | P4、P5 | 06 |

**P7 可与 P3~P6 并行**：尽早把"外网可访问"这件事做掉，因为它是 01 文档的 G5 目标，也是风险最高的环节（域名、证书、端口）。不要在最后才做。

## 10.2 P0 · 设计定稿

**交付物**：`README.md` + `docs/` 下全部文档（**以 README 的文档索引为准，不写死篇数**——同一事实只留一个出处，对应评审 G9 与 [16](16-p1-code-audit.md) 的 E8）。

**验收标准**

- [ ] README 索引中列出的每个文件都存在，且索引链接全部可达（**故意不写死篇数**——见下方新增的「数值一致性」项，写死的数字会随文档链增长立刻过期，对应评审 G6）
- [ ] 跨文档命名一致：`04-database.md` 的每个表名/字段名，在 `05/06/08` 中出现的写法完全相同
- [ ] `05-api.md` 的错误码表与 `06-backend.md` 的 `ErrorCode` 约定一致
- [ ] `02-domain-model.md` 的范围外交集与 `01-requirements.md` 的 OOS 清单无矛盾
- [ ] 随机抽取 5 个接口，能在 `05-api.md` 找到完整字段定义，且其字段都能在 `04-database.md` 找到对应列
- [ ] **数值一致性**：同一事实（表数量、科目数、题量、容量、时长、缓存 TTL、限流阈值、保留天数）在所有文档中**只有一个出处，其余处引用而非复写**；对"复写不可避免"的（如验收命令里的表数量）加 CI 检索断言

> 决策与理由（对应评审 G9）
> 上面最后一条是**流程级**修正，不是逐个改数字。两轮评审共 47 条发现里，属于"数值/计数漂移"的有 6 条（占 13%）：A3 的 `innodb_buffer_pool_size` 在 3 处、A4 的容量在 3 处、D1 的括注算错、D4 的备份保留天数、G6 的表数量在 5 个位置共 7 处。成因完全相同——**同一个数字被两个文档各写了一遍，然后两边各自演进**。
> 逐条改数字只能修好当前这 13 处，下一个改动还会产生新的；而且 P0 原先的 5 条验收项检查的全是"结构一致性"（命名、枚举、字段可追溯），**缺陷出在"数值一致性"上，所以 P0 能"通过"验收却同时存在三组互相矛盾的容量数字**。
> 因此把它写成验收项，并把可自动化的部分（表数量、科目数）落成 CI 断言——这与 [08-ai-pipeline.md](08-ai-pipeline.md) §8.4.4 已采用的 `check-no-corpus-files` 是同一手法。

## 10.3 P1 · 骨架跑通

**交付物**

1. monorepo 目录：`server/`（6 个 Maven 模块）、`web/`、`scripts/`、`deploy/`、`docs/`
2. `deploy/sql/schema.sql`（**27 张表**，含 `exam_paper_sitting` / `exam_session_sitting`）+ `init-data.sql`（20 科目 + 20 卷面模板及其场次与分节 + 管理员 + 系统配置）
3. `deploy/docker-compose.infra.yml`（本地起 MySQL + Redis）
4. 后端：统一响应体 `R`、`ErrorCode`、`GlobalExceptionHandler`、`TraceIdFilter`、Sa-Token 配置、`AuthWhitelist`
5. 前端：工程脚手架、`request.ts`、PortalLayout/AdminLayout、路由表与守卫、登录/注册页
6. `maven-enforcer-plugin` 的依赖约束规则

**验收标准**

- [ ] `docker compose -f deploy/docker-compose.infra.yml up -d` 后 MySQL 与 Redis 均 healthy
- [ ] 执行 `schema.sql` 与 `init-data.sql` 无报错，`SHOW TABLES` 返回 **27 张表**，`rk_subject` 有 20 行
- [ ] **必填列未漏填**：`SELECT COUNT(*) FROM exam_paper_section WHERE duration_min IS NULL OR duration_max IS NULL;` 返回 0（对应评审 G3；同理核查 `exam_session_section` 的 `sitting_no` / `support_status`）
- [ ] `mvn -pl rk-boot -am spring-boot:run` 启动成功，`GET /api/v1/subjects` 返回 code 0
- [ ] 注册 → 登录 → `GET /api/v1/users/me` 全链路成功
- [ ] 未登录访问 `GET /api/v1/users/me` 返回 `2005` + HTTP 401
- [ ] 普通用户访问 `/api/v1/admin/subjects` 返回 `1004` + HTTP 403
- [ ] 拼错一个环境变量名后启动失败并给出明确报错（验证 AC-1 的启动校验）
- [ ] 分层的 `maven-enforcer` 规则生效：故意在 `rk-api` 中引入 `rk-repository`，构建失败
- [ ] 前端 `pnpm dev` 可访问 `/login`，登录成功后跳转首页并保存 token

## 10.4 P2 · 内容结构

**交付物**：科目 CRUD、章节树 CRUD、知识点 CRUD 的管理端页面与接口；考生端的科目列表页、科目详情页、大纲树页。

**验收标准**

- [ ] 管理端可新增/编辑/停用科目；停用后考生端列表不再出现
- [ ] 可维护章节树至 3 层，可拖拽排序（或表单排序），排序结果在考生端一致
- [ ] 导入 3 个热门科目的完整章节树后，考生端大纲树正确渲染（层级、题量显示）
- [ ] 删除有题目引用的章节返回 `1005`，删除无引用的章节成功
- [ ] 知识点标签可新增、编辑 `aliases`、合并；合并后原标签下的题目关联迁移到目标标签
- [ ] 修改科目后 `rk:cache:subject:list` 被清除（通过日志或断点验证），考生端 1 秒内看到变化

## 10.5 P3 · 题库生产闭环

**交付物**：批次管理、Prompt 模板、离线生成脚本、Schema 与质量校验、JSONL 导入、审核工作台。

**验收标准**

- [ ] 管理端可创建批次（选考点、题型、数量、难度），批次状态为 `PENDING`
- [ ] `scripts/generate` 可领取批次、调用模型、产出 JSONL；产出目录中**不存在任何真题文件**（人工检查）
- [ ] Prompt 断言测试：在考点文本中注入"2023 年上半年试题"字样，断言抛异常并终止（GR-1 被单测覆盖）
- [ ] 导入 100 行 JSONL，其中含 3 行非法数据，返回 `{imported: 97, skipped: 3, errors: [{line, reason}]}` 且行号正确
- [ ] 导入后题目状态为 `DRAFT`，重复导入同一批次不产生重复题目
- [ ] 审核工作台可逐题预览（**公式与图片正确渲染**）、通过、驳回、退回重生成、批量通过
- [ ] 裁决后 `rk_question_review_log` 有对应记录，批次计数 `approved_count`/`rejected_count` 正确
- [ ] **软件设计师首批 250 道题走完全流程并 `PUBLISHED`**，`rk_subject.question_count` = 250
- [ ] 相似度检测生效：导入与已有题题干高度重复的题目被拒（`3005`）

## 10.6 P4 · 练习闭环

**交付物**：练习组卷（5 种模式）、答题页、判分、答题上报、错题本、收藏、题目反馈。

**验收标准**

- [ ] 章节练习、知识点练习、顺序练习、收藏练习、错题重做五种模式均可用
- [ ] 答题后即时显示对错与解析；公式与图片正确渲染
- [ ] 答题记录落库，`user_answer_record` 行数与实际答题数一致
- [ ] **服务端复核生效**：手工构造一个把错误答案上报为 `isCorrect: true` 的请求，服务端记录的 `is_correct` 仍为 `false`
- [ ] 答错的题自动进入错题本；同一题连续答对 2 次后状态变为 `MASTERED`
- [ ] **未作答的题不入错题本**
- [ ] 剪断网络后继续答题，恢复网络后记录补传成功；5 秒内重复提交只生效一次
- [ ] 顺序练习关闭页面再打开，可"继续上次练习"且从正确位置开始
- [ ] 游客访问 `mode=SAMPLE` 且 `count=5` 时可用；`count=10` 时返回 `1001`
- [ ] 题目反馈提交成功，同题同用户第 4 次提交返回 `1002`

## 10.7 P5 · 模拟机考闭环

**交付物**：卷面模板配置、模拟考组卷、答题会话、服务端计时、断点续答、分节切换、交卷判分、成绩详情、历史成绩。

**验收标准**

- [ ] 管理端可为科目配置卷面模板；`autoScoredMaxScore` 与客观题分节分值之和不符时保存失败（校验规则生效）
- [ ] 信息处理技术员的「应用技术」分节配置为 `NOT_SUPPORTED`，其分值不计入 `totalMaxScore`
- [ ] 可发起模拟考，试卷题量与章节分布符合配额规则
- [ ] **防重复生效**：同一用户连续发起 3 次模拟考，窗口内重复题的比例显著下降（记录 `repeatedCount` 可观测）
- [ ] 题量不足时按 L4 缩减，前端明确提示"本次试卷共 N 题"
- [ ] 答题卡可跳转、标注已答/未答，分节切换符合 `durationMin` 限制
- [ ] **计时以服务端为准**：把本机系统时间调快 2 小时后，剩余时长不受影响
- [ ] **断点续答**：答题中途刷新页面、换浏览器重新登录，均能恢复全部已答内容与正确剩余时间
- [ ] **高级科目两场次独立计时**（对应评审 A5）：以系统架构设计师发起模拟考时，**场次一结束后不倒计时**，必须用户主动点击「开始场次二（论文）」才开始计时（验证午休不扣时）
- [ ] 两个场次各有独立倒计时与独立 `started_at`；场次一耗尽时长不影响场次二
- [ ] 论文场次 `allowEarlySubmit = false` 时无法提前结束场次
- [ ] 论文分节不可提前交卷（`allowEarlySubmit = false` 生效）
- [ ] 超时后任意接口访问触发自动交卷，会话状态为 `SCORED`
- [ ] 交卷幂等：连点两次交卷只产生一次结算
- [ ] 成绩页客观题显示得分与正确率；主观题分区**不显示分数**，仅展示参考答案与评分要点
- [ ] 历史成绩列表可查看，`ABANDONED` 的会话不出现在列表中
- [ ] 单题作答耗时超过 10 分钟时按 10 分钟入库（`judge.max.duration.ms` 生效）

## 10.8 P6 · 学习数据统计

**交付物**：总览、趋势、章节掌握度、薄弱知识点。

**验收标准**

- [ ] 总览数据与 `user_answer_record` 手工核对一致（做题量、正确率、连续天数）
- [ ] 掌握度符合 6.10.1 的四种场景（可由单测保证，另在页面上人工核对一次）
- [ ] 未做过任何题的科目，掌握度显示 0.5（先验生效），并提供"掌握度含义"说明文案
- [ ] 章节掌握度以树形展示，父节点为其子节点的题量加权
- [ ] 薄弱知识点按掌握度升序，最多 10 条，含"去练习"入口
- [ ] 趋势图缺失日期补 0，切换 7/30/90 天区间正确
- [ ] 新答题后统计页在 5 秒内更新（懒重算生效）

## 10.9 P7 · 公网部署上线

**交付物**：`deploy/docker-compose.yml`、`deploy/nginx/`、`.env.example`、GitHub Actions workflow、上线检查单。

**验收标准**

- [ ] 在目标 VPS 上按 `09-deployment.md` 的"首次上线步骤"从零执行，全程无臆测步骤
- [ ] `https://<域名>` 可访问主页，HTTP 自动跳转 HTTPS
- [ ] 外网设备（手机 4G 网络）可注册、登录、刷题、交卷
- [ ] `sys_user` 之外无法从公网连接 3306 与 6379（`nc -zv <域名> 3306` 超时）
- [ ] `https://<域名>/doc.html` 在生产不可访问（Knife4j 已关闭）
- [ ] 上传一张图片，`https://<域名>/uploads/...` 可访问，且题目中正确显示
- [ ] 容器全部 `restart: unless-stopped`；`docker compose restart` 后服务自动恢复
- [ ] `docker compose logs` 与日志文件均有输出，且达到大小上限后轮转
- [ ] `mysqldump` 备份任务执行成功，备份文件可在宿主机找到；**做一次恢复演练**并验证数据完整
- [ ] `.env` 未进入 Git 仓库（`git check-ignore` 验证）
- [ ] 管理员默认密码已修改

## 10.11 风险登记

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| R1 | **AI 生成题目的审核工作量被低估**，250 题逐题复审是真实的体力消耗 | 阻塞 P3 完成，进而阻塞 P4/P5 | 先做审核工作台（P3 内的顺序已如此安排）；批量通过仅用于明显合格的题目；单批次生成量控制在 50 题以内，避免一次堆积 |
| R2 | 大纲章节树数据整理出错（章节归属错、层级错） | 组卷章节分布错乱、统计失真 | 只做 3 个科目；章节标题只取官方标题短语；组卷对"题量为 0 的章节"自动跳过，不让脏数据阻塞流程 |
| R3 | 科目题量不足以支撑完整卷面（75 题） | 模拟考体验受损 | 已设计 L4 降级 + 前端提示；P3 阶段优先把软件设计师做到 250 题以上再开启 P5 |
| R4 | 单机资源不足（2C4G 同时跑 MySQL + Redis + JVM + Nginx） | 接口变慢或 OOM | JVM `-Xmx1024m` 限死；MySQL `innodb_buffer_pool_size` 限 1024M（与 09 §9.3.1、03 §3.7 一致，对应评审 A3）；Redis `maxmemory` 限 256M；上线后跑一次 `docker stats` 观察 |
| R5 | 版权投诉 | 题目需下架，极端情况下站务受影响 | 护栏 GR-1~GR-3 已在设计层落实；`COPYRIGHT` 类型反馈最高优先级处理；全站非商业 |
| R6 | 计时正确性 bug（如断点续答后时间被重置） | 模拟考成绩不可信，是最致命的缺陷 | 计时全部由 `started_at` 派生、不存增量状态；6.14 已列注入 `Clock` 的单测；P5 验收标准中包含"调快本机时间"与"换浏览器恢复"两项针对性测试 |
| R7 | 环境变量或密钥泄漏进 Git | 服务器被入侵 | `.gitignore` 覆盖 `.env`；上线检查单含 `git check-ignore` 验证；密钥用足够长度的随机串 |
| R8 | 论文模块的长文本把 `exam_session_item` 撑大 | 无明显影响（单卷仅 1 条） | 已用 `MEDIUMTEXT`；单卷体积估算 < 300KB，可接受 |

## 10.12 里程碑到文档的回填责任

| 发生变更的时机 | 必须同步的文档 |
| --- | --- |
| 增删表或字段 | `04-database.md` → 连带检查 `05-api.md`、`06-backend.md`、`08-ai-pipeline.md` |
| 增删接口或改字段 | `05-api.md` → 连带检查 `06-backend.md`、`07-frontend.md` |
| 改枚举取值 | `02-domain-model.md` + `04-database.md` + `rk-common` 的 Java 枚举 |
| 改卷面结构或计时规则 | `02-domain-model.md` + `06-backend.md`（6.9） |
| 改 Prompt 或校验规则 | `08-ai-pipeline.md`（并递增 `prompt_version`） |
| 改部署方式或环境变量 | `09-deployment.md` + `03-architecture.md`（3.5） |
| 前端结构变更（目录 / 组件 / 路由） | `07-frontend.md`（并回填 `03-architecture.md` §3.4 保持一致，对应评审 D8） |

**规则**：文档与代码不一致时，**先改文档再改代码**；不允许"实现先跑起来，文档以后再补"。
